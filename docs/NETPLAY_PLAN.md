# План: сетевой режим (netplay) для MatrixGame

Документ фиксирует, что уже проверено и сделано, и что осталось, чтобы включить игру по сети.
Всё ниже — не идеи, а результат работы с реальным кодом и прогонами; цифры и коммиты настоящие.

## 1. Статус: ядро можно сделать детерминированным

Для сетевого режима в RTS используется lockstep: обе машины крутят **одну и ту же симуляцию**, по сети
гоняются только команды. Значит первый вопрос — детерминизм движка. Ответ: **да, достижим.**

Доказательство (харнесс, 30 секунд боя, карта `armagedd`, сид `12345`):

```
FINAL t=30000 objects=64 rand=1215465 hash=f6d07f754929a996   ← совпало 302 из 302 строк
```

Найдены и закрыты два независимых источника десинка:

| № | Источник | Где | Статус |
|---|---|---|---|
| 1 | Сравнение указателей как тай-брейк | `CollisionCallback`, `MatrixRobot.cpp:2905`, `:3007` | **исправлено**: стабильный `CMatrixMapStatic::m_Id` (коммит `4522edc`) |
| 2 | Чтение неинициализированной памяти | путь движения робота | **обойдено** зануляющим аллокатором под харнессом (коммит `6ea6620`); точное поле не найдено |

Симптомы, по которым это ловилось: стабильный сид и одинаковые команды давали расхождение на 7–17 с
боя, причём тик расхождения «плавал» при пересборке (менялась раскладка кучи) — это подпись адресной
зависимости и/или чтения мусора. Счётчик вызовов `rand()` при этом совпадал идеально.

Что это значит: сеть реалистична, но остаётся инженерная работа — сначала добить детерминизм
(фаза 0), затем слой команд и транспорт.

## 2. Что уже лежит в репозитории

- `MatrixGame/src/SimHarness.{hpp,cpp}` — харнесс (сид, фиксированный шаг, хеш мира, дамп объектов,
  счётчик ГПСЧ, трасса этапов инициализации, фильтр исключений). Инертен без `MATRIXGAME_SIM_HARNESS`.
- `tools/setup-dll.cmd` — подмена `MatrixGame.dll` в установленной игре с бэкапом и сверкой экспортов.
- `tools/start-battle.cmd` — запуск игры с переменными харнесса, логи в `tools/logs/`.
- `AGENT.md`, раздел 8 — краткая памятка по детерминизму и харнессу.

## 3. Фаза 0. Добить детерминизм (в работе)

**Цель:** назвать конкретное неинициализированное поле, инициализировать его в конструкторе и убрать
зануление всей кучи (оно стоит времени на каждом `Alloc` и маскирует другие баги).

Известно на текущий момент:

- поля скорости робота **инициализированы**: `m_maxSpeed`, `m_SpeedWaterCorr`, `m_SpeedSlopeCorrUp/Down`,
  `m_maxRotationSpeed`, `m_GroupSpeed`, `m_ColSpeed` — проверено заливкой `0xCD`, маркер не проступил;
- `m_Forward`, `m_HullForward`, `m_HullRotAngle`, `m_ColsWeight`, `m_ColsWeight2`, `m_SyncMul` — инициализируются в конструкторах;
- `m_BotRotAngle` — мёртвое поле (объявлено в `MatrixObjectRobot.hpp:186`, движком не читается), в нём всегда мусор;
- дифференциальный прогон `0xCD` vs `0xAA` дал первое реальное расхождение на `t=6100`: у робота стороны 1
  разошлись позиция и `m_Speed`, при одинаковых `grp`, `col`, `maxsp` и коррекциях.

Задачи:

1. **0.1.** Расширить `MATRIXGAME_OBJLOG`: добавить `m_HullForward.x/y`, `m_MovePathCur`, `m_MovePathCnt`,
   `m_ZonePathNext`, `m_ZonePathCnt`, `m_DesX`, `m_DesY`, `m_MapX`, `m_MapY`, `m_Cols`, текущие ордера.
2. **0.2.** Прогнать пару `0xCD` / `0xAA` и сравнить дампы: первое различающееся поле на тике расхождения — виновник.
3. **0.3.** Инициализировать найденное поле в конструкторе, убрать `memset` из `CHeap::Alloc`, пересобрать.
4. **0.4.** Контрольные прогоны: два прогона одной карты с одним сидом → хеши должны совпасть
   **без** зануления. Затем то же для 2–3 карт и разных сидов, длительность не меньше 120 с игрового времени.

**Критерий приёмки фазы 0:** три пары прогонов (разные карты/сиды) дают полностью идентичные хеш-логи
без зануления кучи. Время — оценочно 2–4 цикла «правка → сборка → два прогона».

## 4. Фаза 1. Фиксированный тик и гигиена ГПСЧ

- **1.1.** Перенести фиксированный шаг из харнесса в обычную сборку: накапливать реальное время и
  выполнять целое число тиков `LOGIC_TAKT_PERIOD`; рендер интерполировать отдельно.
  Сейчас `CMatrixMapLogic::Takt(step)` съедает остаток произвольной длины
  (`portions = step / LOGIC_TAKT_PERIOD` + остаток) — на разных FPS физика разная.
- **1.2.** Разделить ГПСЧ логики и визуала. Сейчас `rand()` общий, а `RND`/`FRND` (`Math3D.hpp`) вызываются
  в эффектах сотни раз: визуал «съедает» числа, которые нужны ИИ. Ввести отдельный детерминированный
  генератор для логики, сидируемый на матч.
- **1.3.** Убрать wall-clock из логики: `timeGetTime()` в `MatrixSide.cpp:431`, `MatrixFormGame.cpp:173`,
  `MatrixMapPrepare.cpp:1561`. Часть — только статистика/UI, но аудит обязателен.

**Критерий:** при искусственно разном FPS (например, принудительный `Sleep`) хеши всё равно совпадают.

## 5. Фаза 2. Командный слой

Сейчас ввод напрямую меняет состояние (`MatrixFormGame::Keyboard`, `CInterface::LogicTakt`). Для сети нужно:

- структура команды (`SCommand`: тип, сторона, объект/координаты, номер тика);
- очередь команд на сторону, применение в детерминированном порядке на тике `N + K` (лаг ввода 2–4 тика);
- лог команд = реплей (бесплатный инструмент отладки: воспроизвести любой матч по логу).

**Критерий:** локальный матч двух «игроков» через лог команд воспроизводится побитово один в один.

## 6. Фаза 3. Транспорт

- UDP (для RTS предпочтительнее), подтверждение доставки и упорядочивание команд;
- синхронизация тиков: ожидание команд всех сторон до тика `N + K`, «заморозка» при отставании;
- обмен хешем состояния каждые N тиков → раннее обнаружение десинка вместо «разъехалось через 10 минут»;
- реконнект: догон через реплей команд от последней контрольной точки.

## 7. Фаза 4. Оболочка

Лобби (карта, стороны, готовность), пауза, дисконнект/выход, экран статистики. Только после стабильного
транспорта — иначе тестировать нечего.

## 8. Как пользоваться харнессом (для фазы 0)

Сборка:

```bat
cmake -S . -B build-sim -A Win32 ^
  "-DCMAKE_CXX_FLAGS=-DWINDOWS_IGNORE_PACKING_MISMATCH -DMATRIXGAME_SIM_HARNESS" ^
  "-DCMAKE_C_FLAGS=-DWINDOWS_IGNORE_PACKING_MISMATCH"
cmake --build build-sim --config Release
```

Установка в игру и прогон:

```bat
tools\setup-dll.cmd "C:\Program Files (x86)\Steam\steamapps\common\Space Rangers HD A War Apart" --apply
tools\start-battle.cmd run1
tools\start-battle.cmd run2
```

Затем сравнить `tools\logs\run1.txt` и `tools\logs\run2.txt` построчно.

Переменные окружения харнесса:

| Переменная | Смысл |
|---|---|
| `MATRIXGAME_SIM` | автоигра без меню (обе стороны под ИИ) |
| `MATRIXGAME_SEED` | фиксированный сид вместо `time(NULL)` |
| `MATRIXGAME_FIXEDSTEP` | жёсткий шаг логики в мс вместо измеренного |
| `MATRIXGAME_MAXTICKS` | выход по достижении N мс игрового времени |
| `MATRIXGAME_MAP` | принудительная карта, независимо от выбора в меню |
| `MATRIXGAME_HASHLOG` | хеш мира каждые 100 мс |
| `MATRIXGAME_OBJLOG` | дамп объектов (сортирован, чтобы порядок списка не влиял) |
| `MATRIXGAME_TRACE` | этапы инициализации и адрес падения |

## 9. Известные ограничения и риски

- **Standalone EXE не запускается**: компилируется и линкуется, но падает внутри `L3GInitAsEXE`
  (инициализация окна/D3D; адрес падения — `L3GInitAsEXE+0x5FA`). Конфиг из SR2 HD не содержит
  параметров видео, в DLL-режиме они приходят из игры. Для сетевого клиента это придётся починить
  отдельно, либо строить клиент как DLL.
- **Тестов в проекте нет.** Единственная регрессия — харнесс. Любая правка логики = два прогона.
- **Глобальное состояние**: `g_MatrixMap`, `g_MatrixHeap`, `g_Config`, `g_Cache` — один процесс = один мир.
  Для выделенного сервера/нескольких миров потребуется рефакторинг, но для 1 матча на процесс не нужно.
- **Эффекты и логика делят `rand()`** — до фазы 1.2 визуал влияет на последовательность ИИ.
- **ГПСЧ в куче мест**: около 250 вызовов `rand()/Rnd()`; при разделении генераторов нужно
  классифицировать каждый (логика или визуал).

## 10. Открытые вопросы

1. Даёт ли SR2 HD одинаковые стартовые условия при повторном запуске одной карты? Сейчас обходится
   принудительной картой и сидом; для сети надо понять, что именно приходит из игры в `Run(...)`.
2. Влияет ли порядок обхода связного списка логики на что-то ещё, кроме коллизий (поиск целей,
   выбор ближайшего объекта) — нужен аудит после фазы 0.
3. Нужен ли `ASSERT_OFF` в сетевой сборке: сейчас в Release проверки выключены, а рассинхрон лучше
   ловить раньше.
